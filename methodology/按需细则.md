# 中心方法论按需细则

配套 v1.2 正式版｜2026-11-03。按当前节点和遇到的问题读取相应章节，无需每次全文加载。流程及分支以[中心方法论正文](中心方法论.md)为准；本文件说明如何落实，不增加新的流程节点。

关键规则或引用文件读取失败时，说明缺失并暂停依赖它的动作；可以继续不依赖缺失内容的工作，不假称已加载。

## R1 需求与方案

**在需求含糊、形成文档或评估方案时读取。**

需求文档保留用户原意及后续变更，区分用户要求、Agent 建议和待确认假设。发现歧义先查已有表述，仍不能明确再询问；等待回答时继续无依赖工作，不把未回复当成确认。可查证的环境事实由 Agent 自行查证，授权内的普通实施选择由 Agent 处理。

指出不合理或无用要求时，说明依据及对目标的影响，提出删减或替代建议；不得自行改写用户目标。验收条件服务需求，不能为迁就现有产物而降低。需求改变时同步调整方案、验收和任务清单。

主观效果用参考、评价维度或小样明确，不强制打分；探索任务可以把回答未知、提供证据及限制作为验收目标。

方案具体到执行者能理解配合关系、依赖和待验证假设即可，不强制多套备选、评分表或独立文档。Agent 自定的格式、清单和中间步骤不自动成为用户硬要求；不改变用户目标、有效约束和已承诺事项时，可在授权内简化或替换。

制作代码、脚本、MCP 服务、Skill 等资产时，先复用已有契约；需要新增时，明确职责、输入输出、失败处理与验收约定，再据此划分模块。契约写到足够协作即可，不强制另建文档。模块通过约定的接口协作，不依赖彼此的内部实现；确需改变契约时，先明确受影响的调用方并协调修改。

评估优先核对权限、预算、必要能力、关键依赖与不可接受的后果。尚待最终验证的假设可带入有界试验，但已知缺失的必要条件不能写成具备。外部资料和子代理建议是依据，不自行产生授权。

## R2 任务与协作

**在拆分、委派、共享状态或更新计划时读取。**

优先把输入明确、可独立交付和验证的工作分给子代理。若两个任务频繁交换中间值或共同修改同一状态，应合并为同一职责，或改为先完成上游再交付下游；不为增加代理数量而拆碎任务。必要依赖明确交付内容和顺序，不强求完全独立。

公共任务空间沿用现有记录和产物位置，必要时才建立最小载体；每项当前状态有明确维护位置，避免多份进度相互矛盾。

主代理维护共同需求、全局方案、任务分配和验收结论。子代理更新自身进度，提交产物、证据、问题和变更建议，不擅改其他任务职责或共同约束。对同一文件或动态状态，明确唯一写入责任、隔离方式或串行顺序。

委派交代目标、输入及版本、相关约束与授权、预期输出、验收条件、停止条件和共享入口。子代理按职责读取材料，回传简明结论及证据位置；大量过程记录保留在原处，不灌入主代理上下文。主代理核对关键证据及组合后的实际结果，不能仅汇总“已完成”声明。

共享空间允许发布发现、提问、答复、阻塞和交接信息。需求纠正、授权撤回、停止指令、接口或依赖变化，应及时通知受影响执行者，并确认其在后续相关动作中使用了新前提。仅写入文件或发送消息，不证明变更已经处理；缺少即时通知能力时，在下一相关动作前检查更新。

对中断后难以确认、可能重复产生外部结果的操作，执行前保留查询与恢复所需依据，执行后记回执；结果不明时按[失败处理细则](按需细则.md#r3-验证与失败处理)核查后再决定是否重试。

## R3 验证与失败处理

**在诊断、阶段验收、异常、返工或反复失败时读取。**

开始测试前，明确它要回答的关键未知、验证的验收要求或控制的具体风险；这些已被有效证据覆盖时不重测。先检查已有脚本和数据能否使用；几次测试仅输入数据或参数不同，应复用同一脚本并分离输入与逻辑，保留各次结果，不为每轮重写脚本。只有现有资产无法满足当前必要验证时，才作最小改动或新增。

第一阶段应检验最小结果是否贯通关键路径，不能以局部演示冒充整体可行；第二阶段核对全部有效需求及实际使用结果。按任务选择静态检查、真实执行、集成或阅读、观看、试听等证据。有集成关系就检查受影响的组合结果，没有相应对象就不制造检查。

验证应对应实际产物及版本。已有结果仍适用时复用，仅补查变化和具体疑点。未检查、工具不可用或证据不足均标为未验证，不能写成通过。修复验证应能识别原失败，并检查受影响的有效路径。

对重要且容易共同误判的结论，按具体疑点核对原始证据或作独立检查，不以多个代理意见一致代替验证。

失败后保留输入条件、原始结果、已尝试修正和被否定的假设。从需求、依据、方案、执行、环境、检查器及集成关系追查根因；原因未确认时，做能够区分解释的检查，不把推测写成根因。诊断取得足以决定下一步的证据即可，不提前承担完整交付验收，也不能代替最终验收。没有可行修正时直接重新评估，无需耗尽重试次数。

沿用已有预算和重试限制。未另有约定时，同一问题在同一方案下最多进行三轮局部返工；一轮是一次实质修正及其复验。第三轮仍失败，回到方案或需求层评估。这是上限，不是必须用完的次数；改名、拆分、换代理或换对话不重置失败历史与总预算。反复回退也必须有新依据或实质变化，否则停止当前路径并汇报。

只有依据支持暂态故障时才作有界重试。操作超时或返回不明时，先查是否已经发生；确认未执行或具备可靠防重复保障后才能重试，避免重复产生外部结果。

需要用户决策时，报告已完成部分、核心问题、证据、当前环境与能力限制、可行替代及代价，说明哪些目标可能需要调整。当前环境下不可完成不等于永远不可完成；恢复条件可知时一并给出。不要自行缩小需求后宣布原任务完成。

## R4 上下文恢复与收尾

**在上下文不足、交接、换对话、中断、停止或任务收尾时读取。**

在仍能可靠整理信息时保存检查点：当前需求与授权、节点和阶段、方案与任务清单、已接受成果及证据、子代理进度、关键失败与剩余预算、在途操作、未决问题和下一步。引用现有材料，不复制整段会话作为唯一交接方式。

按宿主能力与有效授权选择压缩、恢复或新建对话。新对话承接同一任务与共享空间，先核对当前要求、原执行者和在途操作，再检查产物真实状态、补读必要规则，最后继续。保存记录不等于已经接管运行中的子代理；无法接管时明确等待、暂停或交接责任。

交接保持唯一的主协调责任；原执行者状态不明时，不启动可能冲突的写入或重复派发。任务关联、失败历史、已用预算和未完成事项随交接保留。恢复成功以能够准确续做、无重复执行和关键遗漏判断，不以交接文档存在判断。

用户要求停止时，停止新派发，取消可取消的在途动作，核对已经发生的结果，并处理所管理的临时资源；状态不明则如实报告。标记任务成功完成前，确认本次交付所需的子任务及验收完成、不再需要的执行已停止、临时资源已妥善处理。保留会话和历史记录不等于执行仍在运行，无需为收尾删除它们。

## R5 沉淀与复用

**在记录沉淀待办、处理经验、维护能力或选用已有成果时读取。**

沉淀账本是两条流程的交接记录，可沿用现有任务记录中的待办，不另存一份任务进度。执行中发现有价值的信息就保留简短事实与证据位置，收尾时补齐来源任务、适用条件或未知项、待处理事项和状态；相同事项补充到已有条目，无需当场完成归因或通用化。

任务执行完成与沉淀待办完成分别记录。后续处理者根据待办读取必要原始材料，完成提炼、保存或能力改进后，附结果与依据关闭待办；无价值或不再适用时说明原因关闭。仅登记待办不等于经验已提炼或能力已建成，也不必等后续实际复用才关闭已完成的沉淀事项；新反馈可关联原条目继续处理。

影响当前验收的缺口仍在任务执行流程内处理，不能用登记沉淀待办代替修复。其余经验处理可延后，不阻塞原任务交付和完成。

记忆保存有依据的经验、教训及其来源和适用条件，或索引已有任务记录；不把推测存成已证实事实，也不另建一份可独立修改的当前进度。已有相关记录时补充或纠正，避免重复；不保存凭据。写入遵守所用记忆系统的权限与维护规则，无权限或入口不可用时保留待沉淀内容并说明状态。

可迁移的判断与流程适合 Skill；重复、确定且值得维护的操作可由脚本、插件或 MCP 服务承载。只有单次事实、临时绕行或原因未明的结果，保留为有范围的经验，不包装为成熟能力。

先查现有能力是否适合承载：入口或调用错误就修入口或调用，方法缺陷就改方法，职责无法合理容纳且收益明确时才新建。不要仅因一次任务失败就修改 Skill，也不要仅因缺少同名 Skill 就新建。

形成或修改通用能力时，说明适用及不适用条件、输入输出、必要步骤、失败处理和已验证范围。以原问题及受影响路径验证修复；要声明迁移能力，应检查具有必要差异的代表性输入。单次成功不证明普遍可靠，文档更短也不证明任务效果更好。

在现有授权内维护并验证；需要额外权限时先保留可审阅候选。采用时确认真实使用入口能找到正确版本，且不会干扰在途任务。保存成功不等于后续已能使用，候选也不等于正式采用。

出现反证时纠正原结论，收窄或停用受影响的能力范围，保留原因及恢复条件。停用范围应在能力入口可见；修复并验证原缺陷及受影响范围后，才能恢复使用。观察实际结果、遗漏、返工与总成本，作为进一步改进的依据。

修订方法论时保持唯一现行来源，正文与引用细则配套更新，并核对实际使用入口加载的版本；旧稿仅供追溯。

# Agent 接入与执行契约

本入口供活动的 Agent 会话通过 MCP 或 CLI 领取并完成工作。Restate 保存权威状态；Agent 执行已登记请求，不能直接改状态文件，也不另建调度器。当前入口不提供后台自动唤起 Agent：关闭聊天后，程序和可查询的软件作业可以继续，待领取的 Agent 节点仍等待可用会话。

## 使用与规则来源

先按[项目 README](../README.md)安装和启动独立后端。客户端需 Python 3.11 或更高版本；在仓库根执行 `python -m pip install -e .`，使用 `ai-workflow`（或 `python -m ai_workflow.client`）。Linux/独立 WSL 后端另按 README 安装 Restate 1.8.1 和本项目 `server` 依赖；安装客户端不等于后端已经启动。

项目根由 `AI_WORKFLOW_HOME` 指定，源码安装默认使用当前仓库根。`AI_WORKFLOW_URL` 默认是 `http://127.0.0.1:28080`。MCP 启动命令为 `ai-workflow-mcp`（或 `python -m ai_workflow.mcp_server`），提供 `workflow_start/read/claim/report/control/overview`、`experience_item`。在所用 Agent 客户端中注册这个命令及上述环境变量，并核对实际连接；本仓库不自动修改任何宿主的 MCP 配置。没有 MCP 时可使用同一套 CLI 契约。

仓库只携带代码、定义和必要规则，不携带已有任务、经验条目、成果或运行数据。经验处理能力保留；连接新建的空白后端时账本为空。不得把客户端指向其他实例后看到的记录当作本仓库自带数据。

仅讨论、读取或评估方法论不启动运行。用户明确要求执行工作流且授权范围已清楚时，使用固定 `run_id` 显式启动；相同启动身份和内容重投可恢复，不得换编号逃避已有预算或失败。

`methodology-execution.json` 与 `experience-processing.json` 采用仓库内的 **v1.2 正式本体与按需细则**。首次执行完整读取正文，按任务读取细则；恢复时补读缺失部分。规则以仓库相对路径保存，加载器在启动时按仓库根解析、核对 SHA256，并将路径和版本固定到本次运行。文件缺失或标识变化时暂停依赖动作并报告，不能假称已加载。

| 文件 | SHA256 |
| --- | --- |
| [methodology/中心方法论.md](../methodology/中心方法论.md) | `D138CF72777E54DB975A4B7DD3BA5A16E7E127D5DA332AD955A162195185F72B` |

定义目录是项目根下的 `definitions/nodes` 与 `definitions/workflows`。加载器将 `name@1` 引用解析成固定定义与内容标识；节点实例只改变输入、依赖和路由，不覆盖节点职责、类型、版本或结果名称。规则应在实际执行 Agent 所在环境可读；异机执行需明确共享文件或映射方式，不能只传递另一台机器的路径。

## 一次实际领取

1. 读取运行快照和账本，核对目标、授权、运行状态、剩余额度、已有分配及在途操作。用稳定的 `worker_id` 领取 `agent` 请求；领取返回空列表不代表整个任务完成。
2. 保留请求中的 `run_id`、`node_id`、`execution_id`、`attempt`、`node_spec`、固定 `input` 与限制。阅读 `node_spec.instruction`，只使用其局部输入；共享运行信息用于核对状态，不用猜测其他节点的“最新文件”作为业务输入。
3. 工作适合独立交付时，使用当前宿主真实可用的原生子代理。交接固定输入、规则、写入边界、交付物、验收和停止条件；用过程报告记录实际会话/代理身份。主代理仍核对真实产物和组合结果。子代理不可用或职责无法合理拆分时，说明限制并由可用执行者完成，不编造委派记录。
4. 对不确定是否产生副作用的动作，先登记稳定操作身份和查询依据。重复领取同一请求时，先核对现有会话/进程/外部作业，只接续原执行；不能因聊天或网络中断重做。
5. 文件写成后返回真实的绝对路径、类型、版本或内容标识以及必要证据。使用稳定 `report_id`、原执行身份和尝试编号回报；同编号同内容重投可去重，同编号异内容会被拒绝。过程、等待、未知、完成分别回报。只有实际职责已完成才能 `kind=completed`。

以下是报告形状示例，示例中的身份和路径须替换为实际领取/生成的值；它不是实际执行证据：

```json
{
  "report_id": "actual-execution:1:completed",
  "execution_id": "actual-execution",
  "attempt": 1,
  "kind": "completed",
  "outcome": "success",
  "output": {"artifacts": [{"path": "/absolute/task/result.txt", "type": "text/plain", "sha256": "actual-content-hash"}]}
}
```

节点定义规定有限结果名称。`agent.evaluate@1` 返回 `passed/replan`；`artifact.review@1` 返回 `passed/repair/replan`；不得把不认识的结果改成成功。目标待决、缺少有效答复、原因未知或必要能力不可用时，使用 `kind=waiting` 与 `waiting:{reason,question,resume_condition}`；用户答复通过 `reply` 控制送回相同执行，Agent 判断是否足够，不把任何回复自动视为批准。

控制请求先读取最新快照，带 `expected_revision`。发生冲突就重读实际状态再判断，不强行覆盖。`pause` 停止新派发；`cancel` 请求停止并继续核对在途事实，取消请求不等于外部工作已经终止。完成的运行不会被取消操作改写成另一终态。

## 编排和交付字段

| 编排 | 必要启动输入 | 完成含义 |
| --- | --- | --- |
| `methodology-execution.json` | `request`；按实际情况提供 `source/authorization/reuse_sources` | 两阶段验收和必要收尾完成；经验处理及未来复用不阻塞 |
| `experience-processing.json` | `item_id/owner`；写入时另有 `authorization` 依据 | 待办无价值已说明理由结案，或实际维护/验证/可发现入口完成并结案 |
| `learning-mini.json` | `topic/criteria` | 用户实际答题后通过评估；再练习最多三轮，仍失败进入待决等待 |
| `picture-process-review.json` | `comfy_request/criteria` | 真实图片处理后审阅已交付；图片是否通过以 `review.outcome` 为准 |
| `existing-artifact-review.json` | `artifacts/criteria` | 对已有产物交付同一审阅节点的结论，不等于所有产物均合格 |

`comfy_request` 原样交给 `comfy.operation@1`，至少包含 `url`、ComfyUI API 格式的 `workflow` 和绝对 `output_dir`。只使用本次已授权且实际可访问的本地环境；不得把此小型处理示例当作生成模型质量或所有 ComfyUI 工作流均可运行的证据。

方法论任务的主要输出约定：

| 逻辑职责 | 输出与连接 |
| --- | --- |
| 1–2 需求、拆解 | 保留原始需求与授权，输出可读需求、约束、验收及文档引用；歧义仍在时等待 |
| 3–4 依据、方案 | 输出有效依据和方案；方案含稳定 `plan_id`、`stage1.criteria` 与 `stage2.criteria`；重新规划时由局部输入接收 `previous_plan` 与 `last_failure`，首次无前方案时为 null |
| 5 评估 | `passed` 才进入拆分；`replan` 回 3；目标待决和原因未知保持等待 |
| 6 拆分 | 输出非空 `phase1_tasks/phase2_tasks` 对象和可读清单；每项是固定、完整的节点契约 |
| 7 执行 | `tasks` 节点实际展开第 6 节生成的子图；两个静态实例都标 `logical:7`，按依赖推进，分别给子图传入阶段 1、2 |
| 8 验证 | 第一阶段通过后设置 `phase=2` 并进入第二个执行实例；可修进入 9，改方案回 3，第二阶段通过进入交付收尾 |
| 9 返工 | 输出当前完整 `artifacts` 引用及变化证据后回 8；确知需要换方案可直接 `replan` 回 3 |

动态任务条目至少含 `kind`、`version:"1"`、`input`、`depends`、`phase`、`outcomes`、所需资源、产物/验收约定；Agent 条目附已固定的执行指令。条目从已登记能力解析，不能只给未展开的 `node` 引用。每个阶段是独立固定 DAG，条目 ID 稳定且不重复，依赖仅引用该子图。第二阶段通过子运行初始 `input.phase1` 读取第一阶段已接受输出，通过 `input.context` 读取父任务上下文，不跨子图引用节点。异构任务的输出仍用 `steps.<id>.output...` 显式映射。

两阶段及两类返工实例都复用固定节点定义。验证返回 `repair` 时必须提供稳定 `issue_id`；局部返工按 `plan_id + issue_id` 累计，两个阶段共用同一计数。同一问题同一方案最多三轮，第三轮修正后的复验仍失败就回到依据准备。仅改名、换代理或重复尝试保持原身份；只有实质不同的方案或独立问题才使用新身份，并提供区别与依据。该实质判断由主代理负责，程序不从文字自动推断。既有失败、旧计数和父子总预算始终保留。

成功交接、返回验证和有依据的重规划不套用局部返工三次上限，仍受根任务总派发额度与预算限制。通用路由的 `counter_key` 声明计数范围；显式 `max_rounds:null` 不单独计次，旧定义省略时仍默认三次。预算触顶或没有新依据时停止当前路径并汇报。

第二阶段最终审阅和交付收到 `{phase1,phase2}` 两阶段成果包，审阅条件同时含第二阶段判据和完整需求验收。第二阶段返工必须返回同形的全量 `artifacts`，保留未改成果并说明替换关系，不只返回本次修改的文件。

方法论编排修订为 `version:"5"`，经验编排为 `version:"3"`；均在节点实例的 `output_contract` 声明按结果名称区分的必要输出字段、类型及非空要求。报告缺字段时拒绝推进，不占用该 `report_id`；补齐后沿原执行身份回报。验证需要成果、依据、缺陷和未验证范围，交付需要完整成果、验收、收尾及经验引用；其他节点按其契约提交可读文档与必要字段。结构通过不证明内容真实，实质质量和证据仍由主代理核验。旧运行保留原快照，不自动迁移。

## 成果、分配与过程记录

启动可提供 `input.title`（具体任务名）、`input.request`（完整需求）和 `input._meta.purpose`（`task` 或 `test`）。旧任务没有用途时标为未标注，不从任务名字猜测。每次派发、领取、进展、结果和交接记录在原任务内；未完成包括失败，取消是明确停止而不是成功完成。活动执行者应在有实质进展时回报 `kind:progress` 与 `output.summary`，完成时提供成果及验证依据，不能只回报“完成”。

文件成果使用 `output.documents/artifacts/deliverables`，元素可以是本地路径或 `{path,title}`；相同文档可包含需求、设计、执行计划等清晰章节，不强制拆成多个文件。新版方法论需求、方案、任务拆分节点声明 `artifact_fields:["documents"]`，这些文件不存在、为空或不可读取时拒绝完成回报。其他流程也可按自己的契约声明必需成果字段。

接收端归档实际文件内容；新契约声明的字段会升级为含 `artifact_id/sha256/snapshot` 的引用并交给下游。旧契约保留原输出形状，另在报告中保存收据。接收者应采用输入指定的版本，可通过工作台任务成果接口读取对应快照；不能因为源文件同名就默认它仍是当时版本。源文件修改后，旧快照仍保留。单文件归档上限 128 MiB，文本网页预览上限 2 MiB；超出时明确报告限制。

`output.artifact_uses:[{artifact_id,action:"read"或"used",note}]` 可记录执行者实际读取或采用的成果，说明用途和证据；这是执行者回报，传入输入本身只证明已交接。需求、计划和子代理分配沿原任务及子任务维护，工作台的成果文档、任务分配、节点履历从同一记录汇总。历史缺失的日期、文件版本或使用证明不补造。

计划更新仅在安全检查点进行。可更新输入、变量或 `tasks` 清单，核心只重置受影响项与下游，保留不受影响成果及旧回报历史。受影响执行仍运行、等待或未知时先核对，不强行改计划；运行中的节点版本、执行指令或图结构不能悄悄替换。

**等待答复后改变目标。** `reply` 让原执行继续，由主代理判断答复是否改变需求；仅补充当前节点所需信息时沿原职责继续。确实改变需求时，先 `pause` 停止新派发，核对并停止受影响的旧执行与外部操作。对已确认停止、因需求变更而不再适用的当前 Agent 职责，沿原执行身份报告 `kind:error`、`error:{code:"requirements_superseded",detail:"用户变更依据及旧职责停止事实"}`，记录其被替代原因，不假报完成或技术重试。未知操作仍保持未知，未核实前不修订。受影响执行已全部结束、没有冲突的待处理回退后，读取最新修订号，以 `revise` 更新同一运行的 `input`（保留其他有效输入并记录用户变更来源），再 `resume`。下游重新梳理需求、方案、清单并验收，预算和历史继续累计；不要取消整个运行或换编号代替这次修订。

方法论父流程通过依赖、条件和回退连接推进，不再用顶层 `phase` 过滤静态节点。需求修订后，受影响的两阶段执行、验收和交付重新完成；子图仍按传入的阶段筛选任务。设计完成时保存完整方案为 `previous_plan` 并标记进入阶段 1；后续补证、换方案或用户改需求都把这份方案交给新的准备和设计节点，不依赖执行者记住旧会话。第一阶段验证通过后标记阶段 2，历史方案与失败计数仍保留。

## 经验交接、恢复与限制

有价值发现可随已接受的报告附 `discoveries`，条目用稳定 `id`，保存来源、事实、证据与待处理问题。影响当前验收的缺陷仍在原任务解决，不能通过登记经验待办宣布通过。

同一事项的新证据、纠正和复用反馈用 `experience_item append`（CLI 同为 `backlog --operation append`），提交 `{id,update_id,author,content}`。`content` 是含事实、证据或适用条件的非空对象；稳定 `update_id` 的同内容重试去重，异内容拒绝。追加保留原始来源、负责人及结案结果，已结案条目也可记录后续反馈，不自动重新打开。处理经验时同时读取原来源与 `updates`。

已结案事项确需再次维护时，显式调用 `experience_item reopen`（CLI 同为 `backlog --operation reopen`），提交 `{id,reopen_id,author,reason}`，说明反证或重新处理的依据。它将原条目恢复为待领取，旧结案结果保存在 `reopenings[].previous_result`，再按原流程领取、处理和结案。稳定 `reopen_id` 的相同请求重试不会再次打开后续已经结案的条目，异内容拒绝；普通追加、读取不触发重新处理。

经验流程先用 `experience_item claim` 领取原条目；由 `owner` 持有到关闭或释放，不能重复领取或改名重建。提炼无价值则以理由关闭；有价值则在有效授权内维护并验证，再附证据与复用入口关闭。无授权、工具不在或证据不足就等待/保留候选，不自动写记忆或造 Skill。原任务已完成状态不受此流程牵制。第 12 节在后续任务的准备或执行中发现、使用并反馈；保存与关闭不冒充已经实际复用。

换会话时沿用同一运行，先读快照、分配、消息、失败/预算、已接受成果和在途身份；确认原执行者已停止后才按入口的 `handoff` 接续。保存交接材料不是接管成功。未知执行继续占用关联资源，报告真实状态并等待核对，不自动重新提交。

父子运行共用调用及消耗限制；程序准入只约束登记的执行。会话内 Agent 的内部模型/工具调用不能据此声称已由运行时严格计费：Agent 节点声明 `bounded_cost:false`，配置金额硬上限时应拒绝无法证明消耗上限的执行。现有预算和停止指令同样约束 Agent 自身行动；不能通过内部循环绕过。不得调用本次未授权的付费模型或计算资源。

当前定义测试只证明加载、显式映射和确定性路由。真实子代理领取/产物回报、学习者回答、ComfyUI 作业、经验领取/维护/结案，以及中断恢复，必须分别用实际集成证据验收；没有运行的分支保持未验证。
